# Database Design

## Database Decision

PostgreSQL hosted by Supabase is the final database decision. It replaces SQLite from the original project document so that production data and sessions persist in a hosted environment. The application will use parameterized SQL through a PostgreSQL client; no ORM is required by the project.

## Conventions

- Primary keys use UUID values generated by PostgreSQL or the application.
- Timestamps use `timestamptz` and default to the current time.
- Email values are normalized to lowercase before insertion.
- Role, priority, status, and active-state constraints are enforced in the database and application.
- User-authored text is retained as entered after validation; rendering must escape it.

## Entities and Fields

### `users`

- `id` UUID primary key.
- `full_name` varchar, required.
- `email` varchar, required and unique.
- `password_hash` varchar, required.
- `role` varchar, required; `student`, `support_agent`, or `administrator`.
- `is_active` boolean, required, default true.
- `created_at` and `updated_at` timestamptz, required.

### `faqs`

- `id` UUID primary key.
- `question` text, required.
- `answer` text, required.
- `category` varchar, required.
- `keywords` text array (`text[]`), required with an empty array allowed only when the question is present.
- `is_active` boolean, required, default true.
- `created_by` UUID foreign key to `users`, nullable only for controlled seed data.
- `created_at` and `updated_at` timestamptz, required.

### `tickets`

- `id` UUID primary key.
- `student_id` UUID foreign key to `users`, required.
- `assigned_agent_id` UUID foreign key to `users`, nullable.
- `category` varchar, required.
- `subject` varchar, required.
- `priority` varchar, required; `low`, `medium`, `high`, or `urgent`.
- `status` varchar, required; `open`, `assigned`, `in progress`, `pending`, `resolved`, or `closed`.
- `created_at`, `updated_at`, `resolved_at`, and `closed_at` timestamptz as applicable.

### `ticket_messages`

- `id` UUID primary key.
- `ticket_id` UUID foreign key to `tickets`, required.
- `sender_id` UUID foreign key to `users`, required.
- `message` text, required.
- `created_at` timestamptz, required.

### `chat_sessions`

- `id` UUID primary key.
- `student_id` UUID foreign key to `users`, required.
- `assigned_agent_id` UUID foreign key to `users`, nullable.
- `status` varchar, required; `open`, `assigned`, or `closed`.
- `started_at`, `updated_at`, and `closed_at` timestamptz as applicable.

### `chat_messages`

- `id` UUID primary key.
- `chat_session_id` UUID foreign key to `chat_sessions`, required.
- `sender_id` UUID foreign key to `users`, required.
- `message` text, required.
- `created_at` timestamptz, required.

### `announcements`

- `id` UUID primary key.
- `title` varchar, required.
- `body` text, required.
- `is_published` boolean, required, default false.
- `published_at` timestamptz, nullable.
- `created_by` UUID foreign key to `users`, required.
- `created_at` and `updated_at` timestamptz, required.

### `contact_messages`

- `id` UUID primary key.
- `name` varchar, required.
- `email` varchar, required.
- `subject` varchar, required.
- `message` text, required.
- `status` varchar, required; `new`, `in progress`, or `resolved`.
- `created_at` and `updated_at` timestamptz, required.

### `activity_logs`

- `id` UUID primary key.
- `actor_id` UUID foreign key to `users`, nullable for controlled system events.
- `action` varchar, required.
- `entity_type` varchar, required.
- `entity_id` UUID, nullable when an action has no single entity.
- `details` JSONB, nullable and free of passwords/secrets.
- `created_at` timestamptz, required.

### Session store

`connect-pg-simple` requires a PostgreSQL session table, commonly named `session`, with its package-compatible `sid`, `sess`, and `expire` fields. It is infrastructure for session persistence and is not a user-facing project entity.

## Relationships

- `users` 1-to-many `tickets` through `student_id`.
- `users` 1-to-many `tickets` through `assigned_agent_id`.
- `tickets` 1-to-many `ticket_messages`.
- `users` 1-to-many `ticket_messages`.
- `users` 1-to-many `chat_sessions` as student or assigned agent.
- `chat_sessions` 1-to-many `chat_messages`.
- `users` 1-to-many `chat_messages`.
- `users` 1-to-many `faqs`, `announcements`, and `activity_logs` through creator/actor fields.
- `contact_messages` is independent of `users` because public enquiries are anonymous; it retains the submitted contact details.

## Constraints and Indexes

- Unique index on normalized `users.email`.
- Indexes on `tickets.student_id`, `tickets.assigned_agent_id`, `tickets.status`, and `tickets.created_at`.
- Indexes on `ticket_messages.ticket_id` and `chat_messages.chat_session_id` with creation time for ordered history.
- Indexes on `chat_sessions.student_id`, `chat_sessions.assigned_agent_id`, and `chat_sessions.status`.
- Index on active/published FAQ and announcement states.
- Indexes on `activity_logs.actor_id`, `activity_logs.entity_type/entity_id`, and `activity_logs.created_at`.
- Foreign keys should use deliberate delete behavior: preserve ticket and activity history rather than cascading it from a user; implementation must decide whether deactivation is preferable to deletion.
- Check constraints shall enforce the documented role, priority, status, and contact-message status values.

## Data Integrity Rules

A ticket message sender must be authenticated and authorized for the ticket. A chat message sender must belong to the chat session or be an authorized support user. Only active FAQs are eligible for automated answers. Timestamps and state transitions must be updated in the same logical operation as the action that caused them.

## Applying the Schema

The schema is intended for a new Supabase PostgreSQL database and contains no destructive `DROP` statements. From the repository root, apply it with the PostgreSQL client using a configured connection string:

```bash
psql "$DATABASE_URL" -f database/schema.sql
```

The script enables the `pgcrypto` extension for UUID defaults, creates the nine approved application tables, creates the documented `connect-pg-simple` session table, and adds indexes and `updated_at` triggers. It does not insert seed data or create user accounts.

## Supabase Setup

In Supabase, copy the PostgreSQL connection string from the project database settings and assign it to `DATABASE_URL` in a local environment file or deployment settings. Run `database/schema.sql` from a trusted environment, then verify the tables and indexes in the Supabase Table Editor or SQL Editor. Never commit the connection string or other database credentials.
